Prototype this UI change: $ARGUMENTS

1. Get oriented first: if in a repo, skim the relevant existing components, styles/tokens and `docs/` so the mock matches the real app (colors, spacing, fonts, components). Then invoke the `ui-ux-pro-max` skill for style/palette/typography/UX guidance on each option.
2. Build **one interactive Artifact**. Split the UI into its separate design decisions (layout, navigation, card vs list vs table, density, emphasis, colour, typography, states, mobile layout, interactions…) — surface as many as are genuinely open — and give **each decision 4+ clearly different options** where possible (2 minimum), switchable via tabs/toggles, ideally mix-and-match with a combined preview. Name each option, give a one-line tradeoff, mark your pick. Use realistic content, not lorem ipsum. Make it work at phone width and in dark mode. **Controls never push the preview off-screen:** on desktop put the option controls in a sticky side panel (own scroll) next to the preview; on phones a collapsible bottom sheet; status/variant switchers sit right above the preview. Picking an option must show its effect without scrolling. An option that only shows in one state (e.g. a status, a guest view) switches the preview to that state when picked, and its label says so. Include a "Copy my picks" button that copies decision → chosen option (letter + name) as plain text to paste into chat (clipboard, with select-text fallback).
3. **Write no component code yet.** End with the Artifact link and an AskUserQuestion asking which option (or which mix) to go with.
4. Implement only after I explicitly approve, following the chosen option **exactly**: the mock is the spec. Rebuild every element it shows (dropdown layout, cards, descriptions, extra rows, item order) with the real components. No silent simplifications.
5. Before reporting done, put the mock and the running app side by side (screenshot both), check each element, and list any difference. Fix it, or ask me (AskUserQuestion) before keeping it.
